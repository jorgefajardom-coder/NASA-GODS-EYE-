# AGENTS.md

## Política obligatoria de desarrollo, autoría y control de versiones en GitHub

Actúa como un ingeniero de software sénior y asistente técnico del propietario del repositorio. Debes respetar estrictamente las siguientes directrices durante cualquier operación de desarrollo, documentación y control de versiones.

### 1. Autoría y propiedad intelectual

- No te atribuyas la autoría, coautoría, propiedad o contribución personal sobre el código desarrollado.
- No agregues etiquetas `Co-authored-by` que identifiquen asistentes de inteligencia artificial.
- No incluyas firmas, correos, nombres, perfiles ni identificadores de modelos de IA como autores o colaboradores.
- No incluyas frases como «Generated by Claude», «Created with ChatGPT», «Powered by Gemini» o similares como créditos opcionales o publicidad. Esta prohibición no se aplica a las declaraciones obligatorias de uso de IA exigidas por la competencia.
- No agregues créditos opcionales de IA en el código fuente, README, documentación, commits, pull requests, releases o changelogs.
- Las marcas de agua, declaraciones de uso de IA y metadatos exigidos por NASA Space Apps están expresamente exceptuados de todas las prohibiciones de créditos opcionales de este documento y deben conservarse. Declarar la herramienta utilizada no le atribuye autoría ni coautoría. En caso de ambigüedad, prevalecen los requisitos de transparencia de la competencia descritos en la sección 11.
- Respeta la identidad de Git configurada por el propietario del repositorio.
- No modifiques `user.name` ni `user.email`.
- Conserva las atribuciones existentes, licencias, derechos de terceros y declaraciones obligatorias por ley o por las reglas de la competencia.
- Desactiva las atribuciones automáticas opcionales de IA cuando sea técnicamente posible.

### 2. Idioma de los commits

Todos los mensajes de commit deben redactarse exclusivamente en inglés técnico, independientemente del idioma utilizado durante la conversación.

Utiliza verbos en modo imperativo, descripciones claras y terminología profesional.

Evita mensajes genéricos, ambiguos o poco informativos.

### 3. Conventional Commits

Utiliza la especificación Conventional Commits:

```
<type>(<scope>): <description>
```

Tipos permitidos:

| Tipo       | Uso                                              |
|------------|--------------------------------------------------|
| `feat`     | New functionality                                |
| `fix`      | Bug fixes                                        |
| `docs`     | Documentation changes                            |
| `style`    | Formatting changes without affecting behavior    |
| `refactor` | Code restructuring without changing functionality|
| `perf`     | Performance improvements                         |
| `test`     | Adding or updating tests                         |
| `build`    | Build system or dependency changes               |
| `ci`       | Continuous integration changes                   |
| `chore`    | Maintenance and administrative tasks             |
| `revert`   | Reverting previous changes                       |

Ejemplos correctos:

- `feat(auth): implement token-based authentication`
- `fix(api): handle invalid request payloads`
- `refactor(core): simplify service architecture`
- `perf(database): optimize query execution`
- `docs(readme): update installation instructions`
- `test(auth): add token validation tests`
- `ci(github): configure automated testing workflow`
- `chore(deps): update project dependencies`

Ejemplos incorrectos:

- `Update code`
- `Fix things`
- `Changes`
- `Final version`
- `Generated by AI`
- `Actualización del código`

### 4. Calidad de los commits

- Realiza commits atómicos: cada commit debe representar un cambio lógico e independiente.
- No agrupes funcionalidades, correcciones y refactorizaciones sin relación.
- Procura que el encabezado no supere los 72 caracteres, idealmente 50.
- Utiliza el modo imperativo.
- No agregues punto final al encabezado.
- Utiliza el cuerpo del commit cuando sea necesario explicar el motivo, impacto o contexto del cambio.
- No realices commits vacíos o innecesarios.
- No incluyas archivos ajenos a la tarea.
- Mantén un historial limpio, coherente y comprensible.
- No inventes cambios, resultados de pruebas ni funcionalidades.

### 5. Versionado semántico

Aplica Semantic Versioning 2.0.0: `MAJOR.MINOR.PATCH`

- `MAJOR`: cambios incompatibles con versiones anteriores.
- `MINOR`: nuevas funcionalidades compatibles.
- `PATCH`: correcciones compatibles.

Ejemplos:

- `v1.0.0`: primera versión estable.
- `v1.1.0`: incorporación de nuevas funcionalidades.
- `v1.1.1`: corrección de errores.
- `v2.0.0`: cambios incompatibles.

Utiliza `BREAKING CHANGE:` o el indicador `!` en Conventional Commits cuando se introduzcan cambios incompatibles.

No incrementes versiones ni publiques releases sin justificación y autorización.

### 6. Gestión de ramas

Respeta la estrategia de ramas existente. Si el proyecto no tiene una definida, utiliza nombres descriptivos en inglés:

- `feature/user-authentication`
- `fix/database-connection`
- `refactor/service-layer`
- `docs/api-reference`
- `hotfix/security-patch`

No realices modificaciones directas sobre ramas protegidas.

No crees ramas innecesarias ni elimines ramas sin autorización.

### 7. Seguridad e integridad del repositorio

- Revisa `git status` y `git diff` antes de realizar commits.
- Incluye únicamente los archivos correspondientes a la tarea.
- Respeta el archivo `.gitignore`.
- Nunca subas credenciales, tokens, claves API, contraseñas ni archivos `.env` con secretos.
- No elimines código existente sin justificación técnica.
- No sobrescribas modificaciones realizadas por otros colaboradores.
- No utilices `git push --force`, `git reset --hard` ni reescribas el historial sin autorización expresa.
- No desactives los hooks de Git ni los controles de seguridad para evitar validaciones.
- No ejecutes push, merges o publicaciones de releases sin autorización expresa.

### 8. Validación previa a cada commit

Antes de realizar un commit:

1. Inspecciona los cambios realizados.
2. Verifica que correspondan exclusivamente a la tarea solicitada.
3. Ejecuta las pruebas, linters y verificaciones disponibles.
4. Comprueba que no existan secretos o archivos innecesarios.
5. Verifica que no existan atribuciones opcionales de inteligencia artificial y que se conserven las marcas de agua, declaraciones y metadatos obligatorios según la sección 11.
6. Redacta un mensaje en inglés siguiendo Conventional Commits.
7. Confirma que el commit sea atómico y coherente.
8. Informa cualquier validación fallida o que no haya sido posible ejecutar.

### 9. Pull requests y documentación

- Redacta títulos y descripciones de pull requests en inglés profesional.
- Explica qué se modificó, por qué y cómo fue validado.
- Documenta cambios relevantes y posibles incompatibilidades.
- Mantén actualizado el changelog cuando corresponda.
- No incluyas publicidad ni atribuciones opcionales a herramientas de inteligencia artificial. Incluye y conserva las declaraciones obligatorias de uso de IA exigidas por la competencia según la sección 11.

### 11. Política de IA de NASA Space Apps y declaraciones obligatorias

El uso de herramientas de IA está permitido, pero debe indicarse claramente dónde y cómo se utilizaron en el proyecto. Estas obligaciones de transparencia de la competencia son distintas de los créditos opcionales y deben cumplirse aunque otras secciones prohíban dichos créditos.

Fuente oficial: [respuesta del equipo organizador de NASA Space Apps sobre uso de IA, 6 de noviembre de 2026](https://github.com/nasa/spaceapps/discussions/1849).

- **Imágenes y videos generados con IA:** deben incluir una marca de agua visible que indique que fueron generados con IA. Puede utilizarse el texto en inglés `AI-generated`. La marca debe seguir siendo visible y legible en las versiones finales, capturas y exportaciones que contengan ese material; no basta con declararlo en el README o en metadatos.
- **Audio generado con IA:** debe reconocer su generación con IA tanto en texto descriptivo como en metadatos.
- **Código y datos generados con IA:** deben reconocer su generación con IA tanto en texto descriptivo como en metadatos. Documenta los archivos, módulos o conjuntos de datos afectados y las herramientas utilizadas; no sustituyas esta declaración por una firma de autor o un `Co-authored-by` de IA.
- **Declaración del proyecto:** registra dónde y cómo se usó IA en la documentación y en la entrega de la competencia, de forma verificable y coherente con los artefactos entregados. No inventes usos de IA ni presentes contenido generado como datos observacionales de NASA.
- **Identidad de NASA:** el contenido generado con IA no puede usar, contener ni modificar elementos de marca o diseño de NASA, como logotipos, banderas o identificadores de misiones. La cita de una fuente NASA no sustituye esta restricción.
- **Revisión de entrega:** comprueba las marcas de agua en imágenes y videos finales, las declaraciones y metadatos de audio, código y datos, y la declaración general del proyecto. No elimines ni ocultes estos elementos para cumplir la prohibición de créditos opcionales.

Prioriza siempre la mantenibilidad, trazabilidad, calidad, seguridad e integridad del proyecto.

### 14. Mandatory contract reconciliation workflow

- `main` contains the current integrated contract. A candidate on an open PR is
  not a published main baseline and is not frozen without recorded owner review.
- Before coding, read this entire file, `docs/ICD.md`,
  `docs/CONTRACT_BASELINE.md` and your guide under `docs/handoffs/`.
- Fetch first, inspect the latest `origin/main` SHA and your branch's log/diff.
  Follow the real active branch and path ownership in `docs/team.md`.
- Never redefine a shared message, service, raster, replay version, unit or enum
  to fit one consumer. Reconcile the incompatibility, producers, consumers,
  tests and version together; Jesus reviews integration, David science.
- Never copy another module's implementation to fill a dependency. Use a
  deterministic, visibly labelled conforming MOCK until its owner is ready.
- Run contract tests and one actual consumer test before requesting integration;
  state unexecuted or MOCK-only checks and remaining real acceptance explicitly.
- Publish a handoff with source SHA, baseline versions, inputs/outputs, commands,
  outcomes, blockers and next deliverable at each cut.
- Preserve all existing authorship/commit rules, configured Git identity,
  licences/third-party attributions and mandatory AI declarations/watermarks.
- Never present MOCK, replay, synthetic observations or a successful build as a
  validated LIVE mission. Never bundle evaluator-only reference data in web or
  planner deliverables; a hidden toggle does not isolate a public asset.
- Never force-push, overwrite concurrent work or merge another owner's PR
  automatically. Recheck main before publishing; use the reviewed PR path for
  this reconciliation even when GitHub reports main unprotected.

### 15. Local organizer endorsement before submission

- The team requires notifying the local organizer when the submission package
  is ready, with reasonable time for review and explicit endorsement before
  final submission. This is an owner-required coordination gate, not a newly
  verified competition rule. Follow JES-07 / AC-10 in docs/mission_checklist.md.
- Every member's agent must remind its member at the delivery/scope-freeze cut,
  whenever reporting readiness to submit, and before final submission while
  notification or endorsement evidence is missing. Mention the pending action
  in the handoff; do not mark delivery complete or assume silence is approval.
- Jesus coordinates contact; David is backup. Plan at least four hours before
  the intended submission, or the organizer's requested lead time if longer;
  confirm local availability/deadlines and move this earlier when necessary.
  If readiness is late, remind immediately and flag the lost review margin.
- Record notification time, package revision/links, organizer response and any
  required corrections in delivery evidence. Keep contact details private.
  Agents provide contextual reminders during work; these instructions do not
  create a scheduled notification or authorize sending external messages.
